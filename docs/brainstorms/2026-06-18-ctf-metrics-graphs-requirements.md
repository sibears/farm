# Графики метрик фермы: сплойты, команды, сдача флагов

## Summary

Live-наблюдаемость фермы во время CTF через отдельную Grafana. Бэкенд отдаёт
обогащённые Prometheus-метрики (получено/обработано флагов с разбивкой по
сплойту и команде, % сдачи, текущий бэклог). Детальную матрицу «сплойт ×
команда» и точные кумулятивные итоги Grafana берёт напрямую из Postgres.
Полный стек (ферма + Postgres + Prometheus + Grafana с готовыми дашбордами)
поднимается отдельным `docker-compose.full.yml`.

## Problem Frame

Сейчас бэкенд экспонирует только пять глобальных gauge по статусам флагов
(`flags_accepted/rejected/skipped/queued/waiting`) — без разбивки по сплойтам
и командам. Во время атаки/защиты команде нужно видеть в реальном времени,
**какой сплойт живой и приносит флаги**, **у каких команд их берём**, и
**какие сплойты ломаются** (много reject). Этих разрезов в текущих метриках
нет, отдельной аналитики тоже нет — решения по ходу игры принимаются вслепую.

## Key Decisions

- **Гибрид datasource'ов.** Prometheus отвечает за low-cardinality live-серии
  (получено/сдано по сплойту, по команде, по статусу). Матрицу `sploit × team`
  и абсолютные итоги Grafana берёт прямым SQL из Postgres. Причина: матрица —
  самый детальный и волатильный разрез; держать его в метках Prometheus = риск
  раздувания кардинальности.
- **Событийные счётчики, а не снимок из БД, для потоковых метрик.** Live-сценарий
  требует гладких `rate()`. Следствие: при рестарте бэкенда счётчики Prometheus
  обнуляются, поэтому абсолютные «итого» берём из Postgres, а Prometheus — только
  для скоростей (`rate()` переживает сброс счётчика).
- **Лёгкая защита кардинальности.** Метки нормализуются: `None → "unknown"`,
  число уникальных значений ограничено капом, переполнение схлопывается в
  `"other"`. Строгий реестр сплойтов не вводим — приём флагов не блокируем.
- **Отдельный `docker-compose.full.yml`.** Полный стек живёт в отдельном файле;
  базовый `docker-compose.yml` остаётся лёгким и неизменным по составу.
- **Read-only доступ Grafana к БД.** Для SQL-панелей Grafana ходит в Postgres
  под отдельным пользователем только на `SELECT`.

## Requirements

**Сбор метрик (бэкенд)**

- R1. Бэкенд экспортирует событийный счётчик «получено флагов» с метками
  `sploit` и `team`, инкремент при фактической вставке нового флага в очередь
  (с учётом дедупа — считаются только реально вставленные строки).
- R2. Бэкенд экспортирует событийный счётчик «обработано флагов» с метками
  `sploit`, `team` и `result` (`accepted`/`rejected`/`skipped`), инкремент в
  момент резолва статуса флага в `SendingService`.
- R3. Существующие глобальные gauge по статусам сохраняются (обратная
  совместимость). Текущий бэклог (`queued`/`waiting`) остаётся как общий
  current-state gauge без разбивки по сплойту/команде.

**Кардинальность и метки**

- R4. Значения меток `sploit`/`team` нормализуются перед записью: пустое
  значение → `"unknown"`; при превышении капа уникальных значений новые
  схлопываются в `"other"`.

**Стек и развёртывание**

- R5. Новый `docker-compose.full.yml` поднимает полный стек: ферма, Postgres,
  Prometheus, Grafana. Существующий `docker-compose.yml` остаётся рабочим как
  есть.
- R6. Prometheus в полном стеке сконфигурирован на scrape `/metrics` бэкенда;
  Grafana стартует с провиженными datasource (Prometheus + PostgreSQL) и
  дашбордами.
- R7. Grafana подключается к Postgres под отдельным read-only пользователем
  (доступ только на `SELECT` к данным флагов).

**Дашборды**

- R8. Дашборд содержит панели: получено флагов по сплойту (rate), % сдачи и
  accepted/rejected по сплойту, разрез по командам, общий обзор (бэклог,
  суммарные rate'ы).
- R9. Матрица `sploit × team` рендерится панелью на PostgreSQL datasource
  (SQL по флагам с фильтром по времени), а не через метки Prometheus.
- R10. Абсолютные «итого получено/сдано» используют PostgreSQL datasource
  (точные кумулятивные значения), live-rate'ы — Prometheus.
- R11. Дашборды и datasource провижинятся как код (файлы в репозитории) и
  поднимаются автоматически при старте полного стека.

**Производительность**

- R12. Для SQL-панелей (матрица, итоги) добавляются индексы на колонки
  `sploit` и `team` таблицы флагов, чтобы `GROUP BY`/фильтры не деградировали
  при росте числа флагов.

## Acceptance Examples

- AE1. **Covers R1.** В батче приходят два одинаковых флага одного сплойта.
  **Then:** счётчик «получено» для этого `sploit` растёт на 1 (по фактически
  вставленным), а не на 2 — поведение совпадает с дедупом `ON CONFLICT DO NOTHING`.
- AE2. **Covers R2.** Флаг переходит `WAITING → REJECTED`. **Then:** счётчик
  «обработано» с `result="rejected"` для его `sploit`/`team` +1; % сдачи по
  сплойту считается как `accepted / (accepted + rejected)`.
- AE3. **Covers R4.** Приходит флаг с пустым `sploit`. **Then:** метрика
  пишется с меткой `sploit="unknown"`.
- AE4. **Covers R4.** Число уникальных значений `sploit` превысило кап.
  **Then:** новые значения учитываются под меткой `"other"`, рост числа серий
  Prometheus останавливается.

## Scope Boundaries

- Алертинг (Alertmanager) и нотификации — вне v1, только визуализация.
- Строгий реестр/валидация имён сплойтов — вне v1 (лёгкой защиты достаточно).
- Изменения модели данных флага — не требуются (`sploit`/`team` уже есть).
- Аутентификация/TLS Grafana сверх дефолтов и долгий retention Prometheus —
  вне v1.
- Удаление или рефакторинг существующих глобальных gauge — не трогаем.

## Dependencies / Assumptions

- Команды известны из `config.json` (статический набор) → кардинальность `team`
  низкая; кап нужен в первую очередь как страховка для `sploit`.
- `sploit`/`team` — `Option<String>`, свободные строки от клиента; на практике
  имена сплойтов «в основном стабильны».
- Индексов на `sploit`/`team` сейчас нет — их добавление является частью работы
  (R12).
- В полном стеке Grafana и Postgres в одной сети compose, поэтому read-only
  подключение Grafana к БД технически доступно.
